# Database

ローカル開発ではSQLiteを使い、`database/data/otsuge.sqlite3` に保存します。

本番用ComposeではPostgreSQLサービスを起動し、`database.prod.env` の `DATABASE_URL` をbackendが参照します。

## 通知予定の配信 lease

自動配信と即時送信は、`schedules` の `delivery_lease_token` と
`delivery_lease_expires_at` を使って同じ排他取得を行います。未送信かつ lease が
未取得または期限切れの行を条件付き UPDATE し、更新できたワーカーだけが送信します。
SQLite と PostgreSQL の両方で DB が取得を判定するため、別プロセスでも競合を防ぎます。
期限を過ぎた予定の破棄にも同じ取得処理を使います。

lease の有効期限は **5分** です。各購読者への送信前と、送信待機中も **1分ごと** に
所有権を確認して期限を更新します。Web Push の無通信タイムアウトは **30秒** です。
lease を失ったワーカーは、以降の
送信や予定の完了更新を行いません。送信済み状態と配信ログは同じトランザクションで
保存します。送信済み・破棄済み予定の即時送信は行わず、意図的な再送は別操作として
今後扱います。

ワーカー停止後は最後の lease 更新から5分で再取得できます。再取得時に予定時刻から
30分以上経過していれば、通常の遅延通知と同じく破棄します。外部サービスが Push を
受理した直後、DB に完了を記録する前に停止した場合は結果不明になり、回復後に重複
送信される可能性があります。この仕組みは完全な一回配信を保証しません。

起動時のスキーマ初期化で既存 `schedules` に nullable な lease 列を追加します。
既存の予定や配信状態は保持します。更新中は旧バージョンのワーカーを停止し、全送信
ワーカーを同じ lease 対応バージョンに揃えてから再開してください。
